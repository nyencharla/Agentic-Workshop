# Epic 1 Context: Triage decision schema and seed loader

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

No PRD, architecture, UX or brief exists yet in the planning artifacts directory for this project, so this context is compiled from the epic spec alone. Epic 1 builds the two offline foundations that the rest of the workshop depends on: a strict schema for a triage decision (category, priority, route, rationale) that any later output can be validated against, and a one-command, idempotent loader that puts the seed tickets and customers into the local SQLite database (`app.db`) already read by `mcp/triage_server.py`. Neither piece calls a model or the network — Epic 2's agent and Epic 3's eval both build against this contract and this data rather than defining their own.

## Stories

- Story 1.1: Triage decision schema
- Story 1.2: Seed loader

## Requirements & Constraints

- A triage decision is a JSON object with exactly four fields: `category` (one of `billing`, `bug`, `access`, `performance`, `how-to`), `priority` (one of `P1`–`P4`), `route` (one of `billing-team`, `bug-team`, `access-team`, `performance-team`, `how-to-team`), and a rationale. Any value outside these sets, or any missing field, must be rejected with an error that names the offending field.
- Open in the source spec, not yet decided: whether the schema must also enforce that `route` matches `category` per the policy's one-to-one pairing (see Technical Decisions), whether fields beyond these four are rejected as extra, and whether "one-sentence rationale" is enforced as a literal single-sentence check or just requires a non-empty string.
- The seed loader must be a single command (`uv run python load_seed.py`) that produces `app.db` with `tickets` and `customers` tables holding exactly 24 tickets and 20 customers, matching the headers of `seed/tickets.csv` and `seed/customers.csv`.
- The loader must be idempotent: running it again leaves identical contents, with no duplicate rows.
- `open_tickets` must load as an integer (the triage policy's Enterprise rule compares it numerically to 3); all other loaded columns are text.
- No network calls and no API keys anywhere in this epic — everything is offline.
- `seed/` is read-only and must never be modified by the loader or anything else in this epic.
- Out of scope for this epic: the agent, the MCP tools' own logic, evals, and any UI — those are Epics 2 and 3.

## Technical Decisions

- `app.db` lives at the repo root, is generated by the loader, and is never committed.
- Table and column names are fixed by the existing, unchanged consumer `mcp/triage_server.py`: `tickets(ticket_id, customer_id, created_at, text)` and `customers(customer_id, name, plan, open_tickets)`. The loader must produce exactly this shape so that server keeps working without modification.
- Python 3.12 or newer, dependencies managed with uv (`uv add`, never pip).
- The triage policy defines a fixed one-to-one mapping from category to route: billing→billing-team, bug→bug-team, access→access-team, performance→performance-team, how-to→how-to-team. The rationale a decision carries is expected to name the rule that was applied (e.g. the Enterprise priority bump), which matters for how the schema's rationale field will be used downstream even though this epic doesn't implement that logic itself.
- The policy's Enterprise rule (bump priority one level when plan is Enterprise and open_tickets ≥ 3, capped at P1) is why `open_tickets` must be numeric rather than text — this epic only needs to load that column correctly, not apply the rule.

## Cross-Story Dependencies

- Story 1.1 (schema) and Story 1.2 (seed loader) are independent of each other and can be built in either order.
- Story 1.2's output, `app.db`, is the same database `mcp/triage_server.py` already queries; correctness here is verified through that existing server rather than new query logic.
- Both stories are prerequisites for Epic 2 (the triage agent, which must produce output conforming to the Story 1.1 schema) and Epic 3 (the eval, which reads `app.db` indirectly through the agent and ticket lookups built here).
